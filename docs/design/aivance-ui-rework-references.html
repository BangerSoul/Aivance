05

Implementation blueprint — 5 BYOX phases mapped to this repo

whichever options you pick
P1

Barebones skeleton — token contract

Introduce a single DesignTokens object (spacing, radius, elevation, type scale refs) in core:designsystem/theme; rewire AivanceTheme to consume it. No screens change; all values match today. Gate: :core:designsystem:compileDebugKotlin + existing AccentPaletteTest.

P2

Core state engine — theme selection

Extend ThemeConfig/AccentSeed with the chosen kit (SLATE / AURORA / PAPER) and a FontFamily preference persisted via UserPreferencesRepository — the same DataStore path the notifications work just used. Pure, testable mapping functions.

P3

Protocol & parser — component contract

Harden the shared components (AivanceHeroCard kicker, AivanceEmptyState, StatusChip) against the new tokens: every color/shape flows from the theme, zero hardcoded hex in features (lint gate).

P4

I/O & surfaces — fonts, icons, nav chrome

Ship downloaded font families (res/font + Type.kt), the icon strategy in Destination.icon (paired selected/unselected if I3), and the nav change (N1: 4-item rootDestinations + orb → Assistant). Feature screens inherit; only the bar and hero chrome change first.

P5

Verification gates

Screenshot-compare each workspace (phone/tablet via NavigationSuiteScaffold), contrast audit ≥ 4.5:1 for body text in both ThemeConfig modes, and the existing DestinationTest extended for any bar change. Commit per phase, Conventional Commits.

Suggested combo: Kit B + N1 + F1 + I3 → coherent "AI-native OS" identity Lowest-risk combo: Kit A + N0 + F3 + I1 → polish without IA change Max-identity combo: Kit C + N2 + F2 + I2 → a brand nobody else ships
