# UESF Migration Guide

*Version 1.0.0 · Deliverable 10*

This guide covers the three migrations that matter: **(A)** adopting UESF into an
existing project, **(B)** migrating existing skills into the UESF format, and
**(C)** migrating *between* UESF releases/spec versions.

---

## A. Adopting UESF in your project

UESF is a directory — copy it in, or reference it as a git submodule:

```bash
# Copy (fully yours, editable)
cp -r uesf/ <your-project>/uesf/

# Or submodule (tracked upstream)
git submodule add <url> uesf
```

Then install the skills you need into your agent (see `integrations/README.md`):

```bash
npx skills add ./uesf --skill uesf-co-planning -a claude-code -a codex
```

**Minimum viable adoption** (recommended for new teams):

1. `uesf-co-planning` + `uesf-co-implementation` + `uesf-co-testing` — the core loop.
2. `uesf-co-review` — the merge gate.
3. Run `python3 tools/validate_framework.py` in CI.

**Full adoption** adds governance, meta-skills, and certification (see
`docs/architecture.md` layer map).

## B. Migrating existing skills into the format

If you have skills from another repo (anthropics/skills, superpowers, mattpocock,
your own), migrate them through the intake pipeline — **don't copy files wholesale**
(the framework's standing rule):

1. **Analyze** — `uesf-mk-repository-analyzer`: what does the skill actually do?
2. **Classify** — pick the taxonomy category; check for overlap with existing UESF
   skills (`uesf-le-continuous-learning` screen step).
3. **Synthesize** — scaffold with `tools/skill_scaffold.py`, write the body from the
   template, carrying over the *ideas* with provenance notes.
4. **Verify** — `uesf-mk-skill-validator` to zero errors; `uesf-mk-skill-reviewer`
   for executability.
5. **Version** — `0.x` draft, then promote.

**Field mapping** (foreign → UESF):

| Common foreign field | UESF field |
|----------------------|------------|
| `name` | `name` (keep) |
| `description` (what+when) | `description` (rewrite: when only) |
| — | `purpose` (derive: one sentence) |
| `compatibility` | `context_requirements` + `mcp_tools` |
| `license`, `metadata.version` | `version` (adopt), license in repo root |
| — | `dependencies`, `related_skills` (derive from imports/cross-refs) |
| — | `quality_gates`, `validation`, `rollback`, `failure_recovery`, `acceptance_criteria` (derive from the skill's implicit standards) |

## C. Migrating between UESF releases

1. **Read the changelog** — `CHANGELOG.md` lists breaking changes per release.
2. **Run the validator** — it reports every skill that no longer conforms.
3. **Spec majors** — a compat shim period lets both spec shapes validate; run the
   migration script (generated by the spec-change RFC) at your pace.
4. **Deprecations** — deprecated skills carry `superseded_by` + migration notes;
   move dependents during the grace period.
5. **Re-certify** — after any migration, run the certification engine for the target
   release (`uesf-mk-skill-certification-engine`).

## Rollback for migrations

- Skills: revert the skill commit (draft `0.x` versions make this clean).
- Spec: the compat shim makes spec migration two-directional during the shim period.
- Releases: certified releases are immutable; reverting to a previous tag is always
  supported.
